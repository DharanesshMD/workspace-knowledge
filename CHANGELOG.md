# Changelog

## Unreleased

- Ask for a teammate's work, or a file or module's history: new `knowledge.team_work` tool on the hosted MCP and the `wk-mcp` bridge (and `POST /v1/products/{product}/team-work`). Filters by developer (case-insensitive, unambiguous prefix; an unknown or ambiguous name returns the known developers), files and modules (a path matches that file or everything under that directory), service, `since_days`, keywords and a size cap, over published work in the caller's services, and returns structured entries plus a short brief with `files_reported` and `files_observed` kept apart. `knowledge.share_session` (hosted, bridge and `/v1/share`) takes an optional `files` list (workspace-relative, at most 20, validated and screened) stored in the new `card_files` table (migration 21; re-run `deploy/scripts/application-role.sql` after migrating), so file and module questions work for developers who connect with just a token. The server instructions, tool descriptions and the demo project rule tell agents when to ask and to list their files. Schema version is now 21 in the readiness check and the backup and restore manifests. `verify.py --team-work` checks it on the demo stack.

- Admin tab: a product admin adds a developer in the portal (name, services, reviewer, token lifetime) and gets a one-time message to send them, with the MCP URL, the personal token and ready Claude Code and Cursor setup. The developer never signs in. New `/v1/admin/products/{product}/users` routes (list, create, `/{user}/token` reissue, delete; portal session and CSRF only, off unless `WK_PERSONAL_TOKENS=1`), `/v1/me` gains `is_admin` per product, and migration 20 adds the account functions (re-run `deploy/scripts/application-role.sql` after migrating). Accounts are identities under the reserved issuer `wk-admin-created`; an admin can issue tokens only for accounts they created, within their services scope, and a name already in use is refused. The demo stack creates an `owner` admin (`--admin NAME` / `--admin none`) and `verify.py --admin` checks the whole flow.

- Personal MCP tokens (off by default, `WK_PERSONAL_TOKENS=1`, lifetime cap `WK_PERSONAL_TOKEN_MAX_DAYS`, default 90): a developer creates a revocable token in the portal's Connect page and pastes a ready snippet into Claude Code or Cursor, with no browser sign-in. A token acts as that user on one product's hosted MCP address only; the REST API, token management and every other product reject it. It is sent as an `Authorization` header (the snippets read it from `WK_TOKEN`, so configuration files hold no secret), stored only as a SHA-256, shown once, limited to 5 live tokens per user, and revoked when the membership is removed. New migration 19 (`personal_tokens`; re-run `deploy/scripts/application-role.sql` after migrating), `/v1/tokens` portal routes (session cookie and CSRF only), `/v1/me` gains `personal_tokens`, operator mode `wk-server personal-token`, a `wkpt_` secret-scanner rule, and a threat-model entry for the new residual risk (disabling a user in the identity provider does not revoke their tokens). The `wk-mcp` bridge calls the REST API and keeps its browser sign-in.

- Fixed: the hosted MCP endpoint (`/mcp/{product}`) answered `403 Host header is not allowed` for every request unless the server was reached as `localhost`, because the MCP SDK's DNS-rebinding guard accepts only loopback names by default. The host of the configured `WK_MCP_RESOURCE` is now allowed as well, so deployments on a real hostname work.
- New `deploy/stack/`: `stack.py up|down|status` brings up PostgreSQL, Keycloak, the server and an HTTPS proxy on one Docker host with migrations, the restricted role, Keycloak users, memberships and native MCP sign-in, and is safe to repeat; `verify.py` checks two users end to end through the hosted MCP endpoint; `make-demo-folders.sh` creates one demo project per tool. Guides: [two-developer local test](docs/operations/local-docker-test.md) and [setup by an AI agent over SSH](docs/operations/agent-install.md).

## v0.1.0-alpha.4 — source-only prerelease (draft; not tagged or published yet)

Changes since `v0.1.0-alpha.3`.

- Publish without review, on by default for new setups: a developer's own assistant-written cards (from `wk-agent draft`) are published at once after screening instead of waiting for a reviewer. The server enables every product unless `WK_AUTO_PUBLISH_PRODUCTS=none` (or a list of product IDs narrows it); new collectors (`device connect`, `init`) turn it on unless `--no-auto-publish`; collectors set up earlier stay off until `wk-agent auto-publish enable --yes`. No schema change, recorded in the audit log as `publish_on_submit`, withdrawable. **Behavior change for the alpha.3 default of review-before-publish.** Rule drafts, hook captures, imports, owner sync and `knowledge.record` are never published this way. The portal's source line for assistant cards no longer says they were reviewed.
- Portal **Connect** page: after sign-in, each developer sees their MCP URL per product (`https://<server>/mcp/<product>`, from `WK_MCP_RESOURCE`; the `/v1/me` response gains an optional `mcp_url`) with Copy buttons and ready setup for Claude (custom connector), Claude Code, Cursor and VS Code. Claude's own connectors need an internet-reachable server and are untested.
- Share from your agent with only your sign-in: new `knowledge.share_session` tool (stdio bridge and hosted `/mcp/{product}`, backed by `POST /v1/share`). The agent writes a summary, the server screens it and, where publishing is on, publishes it at once; the conversation itself is never sent. After a project folder is approved once, the bridge's instructions make later agent sessions in that folder pull team context and share on request without asking again; unapproved folders get instructions to ask for approval. Keyword search and `knowledge.context` now match cards containing any significant query word and rank by relevance (they required every word before, so natural-language queries found nothing when semantic search is off).
- Approve a project folder from inside your agent: the stdio `wk-mcp` bridge has two new local tools, `workspace.folder` (is this folder approved, which service subfolders) and `workspace.request_approval` (opens a one-time page on `127.0.0.1`; only the developer's click on Approve records the approval). The approval-writing code moved from `wk workspace approve` into a shared `wk_scope::consent` module with no change to the command. The hosted `/mcp/{product}` endpoint is unchanged.
- Dependencies: `rustls-webpki` 0.103.16 and `webpki-roots` 1.0.11 (fixes for RUSTSEC-2026-0382 and RUSTSEC-2026-0381, published after the previous audit); `cargo audit` now reports zero vulnerabilities and five informational advisories (see [SECURITY](SECURITY.md)).

- No local model is required: rules-mode drafts are marked partial and `[auto-drafted]`, quote bounded conversation text, are screened, and remain private until reviewed. An optional local model remains available. See [setup without a local model](docs/adapters/setup.md#set-up-without-a-local-model).
- `wk-agent prompt --client claude-code|copilot|codex` creates `/wk-summarize` instructions for assistant-written cards; `wk-agent draft` validates and stores them as private drafts for 24 hours. Nothing reaches the team server before review, and a reviewer can then publish them: cards carry a new optional `provenance` (`assistant_written`), the policy advertises `card_provenance`, and `knowledge.record` refuses the field. Upgrade the server before collectors; an older server receives a plain partial draft. Rule drafts, hook partials, imports and truncated cards remain unpublishable. See [Summarize with your assistant](docs/adapters/setup.md#summarize-with-your-assistant-wk-summarize).
- Behavior change: `wk-agent init` and `wk-agent device connect` without `--inference` now select `rules`. Existing configurations remain `local`; rules configurations contain a key older binaries cannot read. A setup's summarizer mode cannot be changed in place.
- New `WK_OIDC_CA_FILE` setting lets the server use an identity provider behind a private certificate authority (previously only public CAs were trusted). The [Keycloak guide](docs/operations/oidc-keycloak.md) records the audience rules and the local qualification; the collector side is `wk-agent device connect --ca-file` (below).
- `wk-agent device connect --ca-file PEM` lets the native collector use a hosted server and identity provider behind a private certificate authority. The validated bundle (certificates only, at most 64 KiB) is stored in private collector state and replaces the public roots for server and provider requests only, with no fallback; existing collector state and approval receipts are unchanged. `wk search` and `wk-mcp` read an explicitly set `WK_SERVER_CA_FILE` the same way. `device status` reports `server_trust`.
- `wk-mcp login --server URL [--ca-file PEM]` signs a developer in once (authorization code with PKCE, loopback redirect) and keeps only a refresh token in the OS credential store; the stdio bridge then renews access tokens silently, so no `WK_ACCESS_TOKEN` has to be copied. The server advertises its provider through `/.well-known/oauth-protected-resource` (new optional `WK_MCP_CLIENT_ID` names the sign-in client); `wk-mcp status`/`logout` inspect and remove the stored sign-in; `WK_ACCESS_TOKEN` remains the fallback when none is stored. The shared PKCE/refresh code moved to a new `wk-login` crate that the collector now uses too (no behavior change). See the [Keycloak quick start](docs/operations/quick-start-keycloak.md).
- A prefilled Keycloak realm ([`deploy/keycloak/wk-realm.json`](deploy/keycloak/wk-realm.json), portal, collector and MCP clients, no stock `account` audience), a Compose override for Keycloak, and `deploy/keycloak/enable-remote-mcp-signin.py` (lets Claude Code and the Cursor agent CLI register themselves and get the MCP audience). `deploy/compose/compose.yaml` now passes `WK_MCP_RESOURCE` and `WK_MCP_CLIENT_ID`, which it previously did not.
- Real-client remote MCP sign-in was tested against private-CA Keycloak: Claude Code 2.1.15 and the Cursor agent CLI 2026.05.24 pass (sign-in, tools, silent renewal); the Cursor editor passed one user-driven run; VS Code 1.142.0 passes sign-in, tool listing and silent renewal in an automated run but needs a realm access-token lifespan above 5 minutes (Keycloak's default 300 s makes it fire dozens of refreshes per sign-in; `enable-remote-mcp-signin.py` now warns). See the [results](docs/reviews/2026-10-19-remote-mcp-signin-results.md) and `scripts/mcp-client-oauth.py`.
- Fixed: `knowledge.record`'s input schema had an untyped property (JSON Schema `true`), which Claude Code 2.1.15 rejected, leaving it with no tools from either MCP endpoint. It is now an object schema.
- Summary quality: the setup guide and README now recommend the assistant-written flow (`/wk-summarize`) with rule drafts as the zero-setup fallback. Rule drafts no longer use a greeting, a pasted trace or code fence, or a bare "ok do it" as the title (45% of cards on a synthetic 20-turn comparison), drop closing courtesies from the rationale and, for replies over 1,500 characters, start at an "In summary"/"TL;DR" paragraph. [`scripts/summary-quality-eval.py`](scripts/summary-quality-eval.py) and the [comparison](docs/reviews/2026-10-19-summary-quality-comparison.md) record the measurement and its limits, including that partial (assistant-written and rule) cards cannot be published.
- Capacity: the hosted database's CPU cap under search load had two causes, both fixed by schema migration 18. Lexical search recomputed `to_tsvector` for every candidate card on every request (the GIN index could never be used under row-level security); it now matches a stored generated `cards.search_vector`, and the prompt-context "similar work" lookup and hybrid retrieval do too (the similar-work lookup now also matches decisions, constraints and open questions). `graph_nodes` gained the `(org, product, card_id)` index its foreign key lacked, which made publication scan the whole table and collapsed writes at about 7,000 cards in a 30-minute soak. The unused `cards_search` index is dropped. Five-identity search p95 fell from about 0.9 s to 34 ms. **Upgrade note:** readiness, `backup.sh` and `restore.sh` now require migrations 1 to 18; take a new snapshot after migrating (schema-17 snapshots need the documented offline upgrade). See the [review](docs/reviews/2026-10-21-capacity-and-search.md) and the small-team [operating envelope](docs/operations/hosted-portal.md#latest-bounded-local-measurement-and-small-team-envelope): local Docker VM, synthetic content, not a forecast.
- `scripts/hosted-pilot.py` takes `--identities N`, `--statement-stats`, `--rare-term-search`/`--rare-term-every`, `--tolerate-errors`, `--server-binary`, `--deploy-scripts` and `--database-events` (checkpoint and autovacuum log lines, no statement text), and records a per-minute timeline; output stays content-free.
- Capture support boundary: one generated [capture support table](docs/adapters/support.md) (client, tested version, OS, status, what is captured, what is held, behaviour on other versions) built by `scripts/support-table.py` from `docs/adapters/compatibility.json`; `--check` fails when it is stale, and README, the setup guide and the completion matrix link to it. `scripts/check-client-releases.py` (weekly workflow `client-releases.yml`) flags Claude Code and Cursor releases newer than the tested versions (at the time of writing 2.1.306 and 3.26.13 against 2.1.293 and 3.23.23). Refusals for unsupported Cursor/Codex versions and non-macOS platforms keep their codes and now add a plain-language `help` message pointing at the table.
- Contact-detail screening no longer mistakes UUIDs, hashes and dates for phone numbers (it could intermittently reject legitimate summaries).

## v0.1.0-alpha.3 — source-only prerelease (2026-10-17)

Published as a GitHub prerelease while the repository was private. Tag `v0.1.0-alpha.3` points to commit [`5b982a5`](https://github.com/DharanesshMD/workspace-knowledge/commit/5b982a5f4523d1e017de4d190586c715538abbe9). It supersedes alpha.1 and alpha.2; no binaries are attached. The tag predates current `main` and is an evaluation candidate, not a production-supported release. See the [release notes](https://github.com/DharanesshMD/workspace-knowledge/releases/tag/v0.1.0-alpha.3).

Known limits at alpha.3 included partial, version-pinned capture; a failed strict model-sensitive contact case; no production OIDC/HTTPS qualification, real-team target-server pilot, long-duration capacity result, signed/notarized macOS distribution, or production security certification. Automatic publication was and remains disabled. See the [production readiness ledger](docs/operations/production-readiness.md) for current status.
