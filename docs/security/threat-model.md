# Threat model and residual risks

Protected assets are developer consent, private conversations, workspace boundaries, team summaries, credentials, and tenant authorization. Treat agents, retrieved text, hook payloads, browser input and imported metadata as untrusted. The operating-system account, credential store, administrator, OIDC issuer and correctly configured OpenBao are trusted. A compromised account or administrator can read process memory or change binaries; this system does not sandbox malicious child commands.

Capture approval and server membership are independent requirements. Personal/mixed sessions must not publish. Raw content remains in encrypted local storage; redaction is probabilistic and review-required mode is available. An authorized cloud client can send retrieved summaries to its provider. Policy must explicitly permit that consumer and destination.

The environment broker authenticates independently to TLS-only OpenBao, rejects redirects and traversal, never sends values to knowledge/MCP, and uses argument arrays. Exact echo suppression cannot prevent transformed output, child files, or network exfiltration. Broker commands should be excluded from capture. Static KV secrets remain in already-running child memory after token revocation. Production profiles and Windows file export are denied in this release. Same-user filesystem races and inherited unrelated environment variables are residual endpoint risks.

Server authorization must run on every request; a frontend toggle is not an access control. Database application roles should not own schema or migrations. Reverse proxy TLS and request limits are mandatory for deployed servers; do not expose internal database or vault ports publicly. Metrics and errors must omit raw payloads and credentials; telemetry is off by default.

Backups can resurrect withdrawn data and old permissions. Restore is isolated, removes memberships, revokes bindings and requires latest deletion-ledger reconciliation before reopening. A ledger older than the last withdrawal cannot prove erasure. Vault recovery is separate and must include auth-policy and token review. See operational runbooks. Exact native OS/client versions, live OIDC/OpenBao revocation, restore disaster drills and independent security review remain release-certification requirements; fixture tests do not establish those claims.

Personal MCP tokens (off by default, `WK_PERSONAL_TOKENS=1`) are bearer credentials that outlive the identity-provider session. A token authenticates one user to one product's `/mcp/{product}` endpoint and to nothing else: every REST route, token management included, keeps requiring a signed identity-provider token or a portal session, so a leaked token cannot publish, review, administer or mint further tokens. Only a SHA-256 of the 256-bit secret is stored; the secret is shown once, has a recognizable `wkpt_` prefix for secret scanners, and expires (at most 365 days, default cap 90). Removing a product membership revokes that user's tokens for the product at once and permanently, and restore deletes every token. Residual risk: disabling a user in the identity provider does not revoke their tokens, so offboarding must remove the membership (which takes effect on the next request) and the operator can shorten the cap; anyone who obtains a token has that user's access to that product until it expires or is revoked. Tokens in shell history, chat or a committed configuration file are the likely leak path, which is why the portal's snippets read the token from an environment variable and never place it in a configuration file or URL.
