# Upgrade and failed migration recovery

Read schema/release notes, pin the proposed artifact, verify its checksum/signature, and record current application/database versions. Stop application writes and take encrypted backups plus a current deletion ledger. Rehearse against an isolated restore with all memberships removed.

Run `wk-server migrate` using the migration role, then start the upgraded app with its ordinary application role. Never give application processes migration-owner credentials. Migrations must complete before traffic is enabled. A migration that adds an application-accessible table also adds its `GRANT` to `deploy/scripts/application-role.sql`; run that file again as the owner after migrating (migration 19, personal MCP tokens, adds `personal_tokens`; migration 20, admin-created developer accounts, adds five administrative functions; migration 21, files reported with shared work, adds `card_files`), or the restricted application role cannot use the new table. Check authorization, withdrawal, private drafts, schema metadata and local queue behavior with synthetic users.

If migration fails, keep traffic stopped. Investigate its transaction and recorded migration version; do not blindly retry destructive DDL or run an old executable against a newer schema. Roll back the binary only when backward compatibility is established. Otherwise restore to a fresh database using the restore runbook, reapply latest tombstones and current policies, then reprovision. No automatic downgrade/zero-downtime guarantee is made.

Migration 22 permanently reserves historical principal names so a new account cannot adopt retained private work or provenance after account removal. Removed token-only principals retain their identity, and the admin cannot create a new account with that retired name. The reservation table is accessible only through the existing administrative functions; it needs no direct application-role grant. Existing function execution grants are preserved. Include these reservations in every current backup and restore. Current recovery tools require exactly migrations 1–22; use tools matching the old schema for the pre-upgrade snapshot.
