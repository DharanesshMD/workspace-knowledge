# Shared service operations

The application supports explicit development and OIDC-backed server modes. It does not issue identity tokens. Use your on-prem identity provider, configure HTTPS issuer/audience/JWKS, and provision the issuer/subject mapping through the administrative CLI. The app ignores token-controlled key URLs and derives organization/user from its own mapping. JWKS load at startup and refresh every 60 seconds from the fixed configured HTTPS URL. A successful fetch atomically replaces the shared key set. Failed fetches retain the last good keys for at most five minutes since their last successful refresh, then authentication fails closed until recovery. Unknown key IDs fail closed without triggering network requests. Duplicate IDs, incompatible key algorithms and non-verification key purposes are rejected. Configure the identity provider to overlap old/new signing keys during its rotation window. Use an HTTPS reverse proxy in front of the HTTP listener.

Run migrations with the migration owner: `WK_DATABASE_URL=... wk-server migrate`. Application mode uses `Knowledge::open` and never runs DDL. Grant the runtime database role only required table/sequence operations; do not give it schema creation, role administration, ownership or BYPASSRLS. Administrative provisioning must run under a separately protected operator database credential. The runtime uses request-local identity settings inside transactions and PostgreSQL row-level security in addition to explicit SQL permission filters. Use `deploy/scripts/application-role.sql` to grant the application role its limited privileges. Owner credentials bypass RLS by PostgreSQL design and must never be used by the HTTP runtime.

Provision one authorized identity by piping a reviewed JSON object to `wk-server provision`: `issuer`, `subject`, `org`, `user`, `product`, `services`, `can_review`. `revoke` with the same identity/product removes membership and bound devices. Do not expose this CLI through HTTP. Updating a grant increases its policy revision; previously queued submissions must be reviewed under the new policy. Backend authentication validates issuer, audience, expiry, not-before and allowed signature algorithms before identity lookup.

Start `wk-server --production` with `WK_DATABASE_URL`, `WK_OIDC_ISSUER`, `WK_OIDC_AUDIENCE`, and `WK_OIDC_JWKS_URL`. `WK_BIND` defaults to loopback. `WK_WEB_DIR` serves the built console directory; `WK_CONSOLE_ORIGIN` permits exactly that browser origin. No credential-bearing cross-origin allowance is configured. Hosted browser authentication uses opaque HttpOnly cookies; agent/API clients retain per-request Bearer authentication. Protect the reverse proxy and static bundle as part of the deployment boundary.

Environment metadata is an operator-managed strict JSON array in `WK_ENV_SCHEMA_FILE`: each record contains `org`, `product`, `id`, `name`, `service_ids`, `variables` (name, required, description). Do not put values, tokens, vault paths or personal content in this file. The API filters it by tenant and every service permission. Secret authorization remains the independent OpenBao policy on each broker operation; seeing a schema does not grant values.

Corrections use `card.base_revision`, reset the corrected card to an unpublished draft, invalidate graph nodes and stale prior evidence. Withdrawal writes a tombstone and removes retrieval/graph visibility. Restore must replay the latest tombstone journal, not merely the journal inside an old backup. Graph provenance declares source type, boundary, coverage and reported status. Trusted test evidence is accepted only through an internal operator/connector method; no public API can mark its own report verified. That method is not a signed repository connector by itself.

## Reviewed relationships and evidence

`POST /v1/products/{product}/relationships` accepts exactly `source_card`, `target_card`, `source_revision`, `target_revision`, and `kind`. Supported kinds are `contradicts`, `depends_on`, and `supersedes`. The source supersedes the target. Both cards must be published, active and visible in every service to the current reviewer. Requests lock the cards in stable ID order, recheck both revisions, and commit atomically. Stale revisions return 409; inaccessible endpoints return 404.

Conflict/dependency links are idempotent. Supersession adds a new historical revision to the target, marks its evidence stale, and excludes it from ordinary search/context retrieval. Explicit authorized get/history and graph views retain the old card. Supersession does not automatically restore an old card if its replacement is withdrawn. Corrections and withdrawals remove affected graph links. Republishing or reconciling an unchanged card preserves reviewed links. Relationships are never inferred from text similarity; an explicit reviewer action is required.

`GET /v1/products/{product}/cards/{id}/evidence` returns at most 100 trusted evidence references with provider, immutable code revision, evidence kind, card revision and staleness. It excludes internal metadata, commands and connector payloads, and enforces both current and historical service scopes. This is separate from author-reported evidence in the card body. Evidence attestation remains an operator/verified-connector library boundary, with no public promotion endpoint. Signed external connector verification remains unfinished.


## Hosted browser identity

Set `WK_BROWSER_CLIENT_ID` to a registered authorization-code OIDC client and, for confidential clients, supply `WK_BROWSER_CLIENT_SECRET` through the deployment secret manager. Empty/unset secrets select public-client token exchange; public clients send their client ID without Basic authentication. The discovery issuer is the fixed `WK_OIDC_ISSUER`; register exactly `WK_CONSOLE_ORIGIN/auth/callback` as its redirect URI. The browser client ID may differ from the API's `WK_OIDC_AUDIENCE`. Grant the registered client only `openid`; no upstream access, refresh or ID token is retained after verified issuer/subject extraction. Identity mappings and memberships must already be provisioned by the protected administrative CLI. No display-name, organization or membership claim from the provider grants application access.

Production requires HTTPS for console origin, issuer and discovered authorization/token/JWKS endpoints. The same-origin reverse proxy terminates TLS, forwards cookies and preserves browser Origin headers. Do not rewrite Origin, cache `/auth/*` or `/v1/*`, or log callback query strings, cookies or Authorization headers. Restrict request sizes, login/request rates and upstream connections at the proxy. The app binds behind the proxy; it does not trust forwarded headers to choose callbacks. `--dev` accepts a synthetic provider only with explicit `WK_BROWSER_TEST_ISSUER` and literal loopback HTTP; never include that variable or development credentials in production.

Production cookies are `__Host-wk_session` and `__Host-wk_login`, Secure/HttpOnly/SameSite=Lax, Path=/, no Domain. Transactions last five minutes, are browser-bound and single-use, and are bounded to 1,000 pending records per process. A restart invalidates pending logins; an initial deployment uses one application process, so no shared login transaction store is required. Metadata refreshes after 60 seconds when authentication is attempted, with a five-minute maximum stale snapshot. Failed refresh attempts also have a 60-second cooldown, shared by concurrent logins. Existing portal sessions do not retain provider tokens. Sessions expire after 30 minutes idle or 12 hours absolute, and each identity has at most ten active sessions. Membership/identity is resolved anew per API request. Opaque 32-byte session IDs are stored only as SHA256 hashes; the CSRF token is derived with domain separation and its hash is checked. Cookie-authenticated mutations require exact Origin and `X-CSRF-Token`. Mixed cookie/Bearer credentials are rejected. MCP accepts only Bearer credentials.

Migration 6 creates `browser_sessions`. Apply migrations with owner credentials, then reapply `deploy/scripts/application-role.sql`. Session rows have no Actor RLS because identity is resolved before an Actor exists; only the protected authentication service uses random hash lookups. The application role can manage session rows and read identity mappings, but cannot provision identities or memberships. Advisory transaction locks serialize session creation without granting UPDATE on identities. Database/host operators remain trusted; hashes do not make a compromised application role harmless.

Logout invalidates the current portal session and expires its cookie. It does not revoke other devices/sessions or log out the OIDC provider. There is no provider-token refresh or arbitrary post-login redirect. A configured provider outage prevents new login; valid portal sessions continue until their local deadline or application authorization changes. Multi-replica login, OIDC front/back-channel logout, production-provider rotation acceptance and five-developer load certification are not implemented by this increment.

## Owner-only summaries

Migration 7 adds the isolated `personal_summaries` table and protected capacity helper. Reapply the runtime grant script after migrating. Owner/org/product and every current service permission are enforced by explicit queries and RLS. Reviewer permissions confer no private access. JSON input is strict, bounded and privacy-screened; captured content must be complete, and manual notes must be proposed without invented evidence. Runtime access does not include DELETE.

`/v1/products/{product}/personal` supports create/list; `/{id}` supports detail, revision-checked edit and deletion; `/{id}/submit` creates an unpublished review card atomically at the expected revision and current policy. Repeating that transition returns the same card; changing policy creates a separate current-policy review copy. Private edits never mutate existing shared cards.

Retention is a fixed 30 days from creation; retries and edits do not extend it. Logical expiry denies access. Deletion clears the body but retains an idempotency marker to prevent replay resurrection. At most 2,000 live summaries per owner/product are allowed, including records hidden after service narrowing, with a 64 KiB stored JSON cap. Physical expiry cleanup and personal deletion replay after backup restore are still required in the operations increment before rollout. Database/backup operators are trusted; this is application privacy, not end-to-end encryption.

## Team browsing

GET `/v1/products/{product}/context` returns only published, nonwithdrawn shared cards, plus authorized author IDs and creation/work time. Strict query fields are `author`, `service`, `since_ms`, exact relative `file`, and UUID `before`. Both rows and pagination anchors enforce current org/product/every-service scope and filter eligibility. Pages are chronological and capped at50; no total count or hidden-member directory is exposed. GET `.../activity` coexists with existing opt-in POST/DELETE and returns up to50 active unexpired reports, allowlisting safe intent/files/service/timestamps without session IDs. The owner summary store is never queried by either route.
